# PremierOS Garments — المرحلة الخامسة: مدير المصنع واستقبال طلبات سحابي معزول

## ما تم بناؤه

- مصنع مستقل في المشروع المشترك **AMMCO** دون تعديل جداول المؤسسة الأصلية أو أدوار AMMCO أو مشغل إنشاء حساباتها.
- عضوية موظفين لكل مصنع بأدوار: `owner`، `manager`، `sales`، `production`، `inventory`، `viewer`. إسناد هذه الأدوار يتم بواسطة مدير قاعدة البيانات في الوقت الحالي، وليس من الواجهة.
- جداول جديدة فقط: `garment_factories`، `garment_staff`، `garment_intake_orders`.
- تمكين RLS مع `FORCE ROW LEVEL SECURITY` لكل جدول؛ العضو النشط يرى المصنع الخاص به وطلبات استقباله فقط.
- المدير أو المبيعات يستطيعان إضافة طلب عميل بحالة `new` فقط؛ لا يوجد إذن تحديث أو حذف في هذا الإصدار.
- التحقق الخادمي من حجم البنود وأكواد SKU والكميات والأسعار وحدود المدخلات. تاريخ إنشاء الطلب ومستخدمه وحالته تحددها قاعدة البيانات عند الإدخال.
- شاشة **طلبات العملاء السحابية** في GitHub Pages لتسجيل الدخول، ثم جلب الطلبات المحفوظة مركزيًا وإدخال طلب أولي.

## بيانات الدخول

استخدم **حساب Supabase Auth الموجود مسبقًا** المرتبط بالمصنع، وبريد الحساب وكلمة مروره من المستخدم نفسه فقط. لا ترسل كلمات مرور عبر GitHub أو المحادثة. يتم الاحتفاظ برمز الدخول في ذاكرة المتصفح فقط، وينتهي تلقائيًا عند انتهاء الجلسة.

قاعدة AMMCO تحتوي على مشغل لإعداد حسابات AMMCO عند إنشاء مستخدم جديد؛ لذلك **لا يوجد تسجيل حسابات جديدة من تطبيق الملابس** في الوقت الحالي. يُراجع المشغل ويُفصل أو يُعدَّل بصورة مخططة قبل إضافة أي موظف جديد.

## كيفية إنشاء أول طلب

1. افتح رابط المعاينة `https://premieros.github.io/e.magdy/`.
2. انتقل إلى **طلبات العملاء السحابية**.
3. سجّل الدخول بحساب العضو الموجود مسبقًا.
4. اضغط **تحديث من السحابة** لعرض المصنع.
5. اضغط **طلب عميل جديد**. أدخل العميل والتواصل، ثم اكتب سطرًا لكل SKU بصيغة:

   `SKU | المقاس | اللون | الكمية | السعر`

   مثال خيالي: `SH-101-M-BLK | M | أسود | 12 | 350.00`
6. احفظ الطلب وتحقق من ظهوره بعد التحديث.

الحفظ السحابي **مستقل عن بيانات المصنع التجريبية في `localStorage`**. إذا كان وضع العرض الافتراضي نشطًا، تُعطّل كتابة طلبات حقيقية من الواجهة نفسها حتى يحذف المستخدم العرض أولًا.

## قيود حرجة قبل تسليم التشغيل الإنتاجي الكامل

- هذه المرحلة توفر **استقبال طلبات مركزيًا مع عزل أساسي**، ولا ترحل الطلب تلقائيًا إلى إنتاج المصنع المحلي.
- الطلبات السحابية **غير قابلة للتعديل أو الاعتماد أو الإلغاء من التطبيق** بعد إنشائها حتى تُنفذ دورة حالات مدققة ومعاملات خادمية.
- لم ننقل الموديلات والمخزون والقص والعمال والجودة والتكلفة ومبيعات الجملة المحلية إلى قاعدة مركزية بعد.
- لا توجد حجوزات مخزون مركزية أو تحويلات أو فواتير وضريبة أو دفتر حسابات متكامل.
- يجب اختبار دخول حقيقي من المتصفح على جهازين، وتوافق سجل الطلبات بينهما، والتحقق من رفض المستخدمين غير الأعضاء، وتدقيق الاسترداد والتقارير قبل اعتمادها لتسجيل طلبات حقيقية دون إشراف.
- فحص Supabase Security Advisor أظهر أن **حماية كلمات المرور المسربة معطلة على مشروع AMMCO**. المرجع: https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection
- المستودع عام، لذا لا تُخزن كلمات مرور أو مفاتيح `service_role` أو معرّفات أسرار في الكود. المفتاح `sb_publishable_` المخصص للمتصفح مسموح؛ الوصول يتحكم به RLS.

## التحقق المنفذ

- صلاحية الحساب موجودة ونشطة في جدول العضويات.
- سياسات RLS مفعّلة وإجبارية على الجداول الثلاثة.
- محاكاة `authenticated` بهوية المدير رأت مصنعًا واحدًا وعضوية واحدة.
- محاكاة مستخدم غير عضو لم ترَ أي مصنع أو عضوية أو طلب.
- أجري إدخال طلب تحت صلاحية المدير ثم `ROLLBACK` فلم تُحفظ بيانات اختبار في قاعدة العمل.
- تحققت دالة PostgreSQL من طلب صالح ورفضت الصفر والسعر الناقص والدقة الزائدة.
- اختبارات JavaScript تعمل باستخدام HTTP مُحاكى وليست بديلًا عن اختبار تسجيل دخول حقيقي.

## التوسع التالي

1. تدفق دعوة موظفين منفصل عن حسابات AMMCO.
2. جداول موديلات وأصناف مركزية بارتباط المصنع.
3. دورة الطلب من جديد إلى معتمد إلى الإنتاج في معاملات PostgreSQL آمنة.
4. مخازن وحركات خامات ومنتج تام بعمليات ذرية، ورصيد متزامن بين الموظفين.
5. سجلات تدقيق ونسخ استعادة اختُبرت وبيئة نشر ذات بوابة تسجيل دخول تغطي جميع الشاشات.
